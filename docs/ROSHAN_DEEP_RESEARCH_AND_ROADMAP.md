## 1. الخلاصة التنفيذية

Roshan تطبيق عيادة/مركز طبي متكامل نسبيًا يجمع EMR/العمل السريري، إدارة المرضى والزيارات والطوابير، المختبر، الوصفات والصيدلية والمخزون، الفواتير والمدفوعات والصندوق والموردين والتأمين، وإدارة المستخدمين والصلاحيات والفروع. البنية الحالية هي React 19 + TypeScript + TanStack Start/Router + Vite + Tailwind CSS 4 + مكونات Radix/shadcn-style + Supabase PostgreSQL/Auth/JS + Vercel. هذه بنية مناسبة لتطبيق ويب سريع موجّه للهاتف إذا استمر ضبط SSR والصلاحيات والأداء.

**الاستنتاج الاستراتيجي:** لا يُنصح باستبدال المشروع بمنصة عامة أو إنشاء تطبيق موازٍ. أفضل عائد يأتي من تثبيت مسار الترحيلات وقابلية إعادة بناء قاعدة البيانات، إغلاق بوابات النشر السريري، مراجعة كل RPC ذات صلاحيات مرتفعة، ثم تحسين تدفقات الطبيب والاستقبال والصيدلي والمختبر وفق قياس فعلي لعدد النقرات والأخطاء والزمن.

## 2. نطاق الفحص وحدوده

### ما فُحص مباشرة
- شجرة المستودع على `main` (466 مسارًا في لقطة الشجرة)، مع README، خطة التنفيذ الرئيسية، خريطة الأدوات، سجل مطابقة الترحيلات، وملف الحزم.
- بنية المجلدات `src/` و`tests/` و`db/` و`docs/recovered-migrations/` وملفات CI.
- بيانات مشروع Supabase الحي، الجداول وسياسات RLS، ملخص الدوال والمحفزات والإضافات وStorage وRealtime، سجل الترحيلات، Edge Functions، وتنبيهات الأمان والأداء.
- بحث الويب في OpenEMR وMedplum وOpenMRS وFrappe Health/ERPNext وCliniko وJane وSimplePractice، إضافة إلى نقاشات Hacker News ومصادر GitHub.

### ما لا يجوز الادعاء بأنه مكتمل
- لم تُثبت إعادة تشغيل تاريخ الترحيلات بالكامل على قاعدة فارغة؛ الخطة الحالية تسجل صراحة أن baseline نظيفًا لم يُثبت وأن ترحيل ربط هوية تاريخي واحدًا منقح لحماية معلومات بيئية.
- لا يمكن استنتاج إعدادات Auth Dashboard الحساسة كلها من كتالوج SQL وحده. لا توجد Edge Functions منشورة بحسب API المتصل، لكن ذلك لا يغني عن مراجعة إعدادات Auth/redirect URLs/SMTP/rate limits من لوحة المشروع.
- لا توجد Storage buckets أو Realtime tables منشورة في القراءة الحالية؛ هذا لا يثبت أن التطبيق لا يستخدم أي آلية أخرى للملفات أو التحديث.
- لا يمكن اعتبار `main` مساويًا للنشر الفعلي؛ آخر سجل موثق يشير إلى تأخر deployment عن المصدر.
- لا أصف التطبيق بأنه جاهز للاستخدام مع بيانات مرضى حقيقية قبل إغلاق بوابات النشر، النسخ الاحتياطي والاستعادة، اختبارات الصلاحيات، واختبارات سير العمل السريري.

## 3. قراءة المعمارية الحالية

### 3.1 طبقة التطبيق

المؤشرات من `package.json`:
- Node `22.x`، TypeScript، React `19.x`، TanStack Start/Router، Vite 8.
- `@supabase/supabase-js`، `@tanstack/react-query`، React Hook Form + Zod، Radix UI، Tailwind CSS 4، Recharts، Lucide.
- اختبارات Node مخصصة عبر `node --test --experimental-strip-types`، مع اختبارات لأدوار المستخدمين، البحث والتنقل، SSR log redaction، الفوترة، الوصفات، المخزون، RLS والتدفقات السريرية.

**نقاط قوة**
1. TypeScript واختبارات حراسة صغيرة ومحددة تمنح أساسًا جيدًا لتقليل الانحدارات.
2. اعتماد React Query مناسب لإدارة cache وطلبات البيانات، بشرط توحيد مفاتيح الاستعلامات وسياسات الإبطال وعدم الاحتفاظ بسياق مريض عند تبديل المستخدم أو الفرع.
3. React Hook Form/Zod يتيحان توحيد التحقق من المدخلات. يجب أن تظل قواعد الصحة والمال والصلاحيات مُتحققًا منها في الخادم/قاعدة البيانات أيضًا.
4. مكونات الواجهة القائمة تقلل الاعتماد على مكتبات واجهة إضافية؛ لا تضف مكتبة ضخمة لمجرد تنفيذ نمط موجود.
5. وجود اختبارات SQL للتزامن والذرية المالية والفرعية أكثر قيمة من اختبارات snapshot سطحية وحدها.

**مخاطر/نقاط تحتاج تدقيقًا**
- لا يوجد مجلد `supabase/` في شجرة `main` التي فُحصت. مصدر SQL موزع بين `db/` و`docs/recovered-migrations/`؛ هذه نقطة حوكمة أساسية لأن تسلسل المصدر القياسي غير واضح.
- لا يجوز افتراض أن كل استدعاء قاعدة بيانات يمر عبر RPC آمنة؛ يجب ربط كل شاشة بمسار الكتابة الفعلي واختبار أن الواجهة لا تستطيع تجاوز RPC المخصصة.
- يجب التحقق من حدود Server/Client في TanStack Start، تخزين الجلسة، حماية أسرار الخادم، redaction للأخطاء، وتفادي تسريب البيانات في SSR أو logs.
- يلزم توحيد التعامل مع `branch_id` والفرع الحالي، وإبطال cache عند تغيير الدور أو الفرع أو تسجيل الخروج.
- وجود جدولين مثل `medicines` و`medicines_2` يوجب مراجعة توافق تاريخي وخطة إزالة تدريجية، لا حذفًا مباشرًا.
- يجب مراجعة اعتماديات beta مثل `nitro` بما يتفق مع الإصدارات المثبتة واختبارات البناء الفعلية.

### 3.2 نموذج المجال

المجالات المرصودة من الجداول والوثائق تشمل:
- الهوية: `users`, `profiles`, `roles`, `permissions`, `role_permissions`.
- تعدد الفروع: `branches` وعلاقات الفرع على كيانات التشغيل.
- السجل السريري: `patients`, `visits`, `vitals`, `clinical_notes`, `diagnoses`, `followups`, `appointments`, `queue_tickets`.
- المختبر: `lab_orders`, `lab_order_items`, `lab_tests`, `lab_parameters`, `lab_results`, `lab_reference_ranges`.
- الأدوية: `prescriptions`, `prescription_items`, `medicines`, `pharmacy_inventory`, `stock_movements`.
- العمليات والإجراءات: `procedure_orders`, `procedure_results`, `procedures_catalog`, `medical_certificates`, `certificates`, `attachments`.
- المال والتأمين: `invoices`, `invoice_items`, `payments`, `cashbox_transactions`, `expenses`, `supplier_bills`, `supplier_payments`, `insurance_claims` وعناصرها ومدفوعاتها وقواعد التغطية.
- الإدارة: `departments`, `employees`, `services`, `system_settings`, `audit_logs`.

وجود بعض المفاهيم المتقاربة (مثل `certificates` و`medical_certificates`) يستدعي توثيق مصدر الحقيقة لكل مفهوم وتحديد هل هما كيانان مختلفان أم إرث توافق. لا يُجرى دمج قبل قراءة جميع المراجع والبيانات واختبارات التوافق.

## 4. قاعدة البيانات وSupabase: أهم الملاحظات

### 4.1 سجل الترحيلات وإعادة البناء

الحالة الحية 109 ترحيلات، لكن الوثائق تقول إن مطابقة المصدر التاريخي ليست برهانًا على replay نظيف؛ 92 تطابقًا في لقطة قديمة، استثناء تاريخي واحد منقح، ثم ترحيلات لاحقة، كما أن بعض الترحيلات الأولى تفترض وجود كائنات سابقة. كذلك `live_sql_hash_verified=false` مقصود لأنه لا توجد مقارنة كاملة للـSQL المخزن الحي مع المصدر.

**الأولوية P0:** إنشاء خط ترحيلات قياسي قابل للتكرار، مع:
1. baseline موثق ومراجع من schema الحي.
2. manifest يربط كل version بمصدره وSHA-256.
3. فصل أي بيانات هوية بيئية عن DDL القابل لإعادة التشغيل.
4. تشغيل replay على PostgreSQL 17 نظيف ومجاني/محلي أو CI، لا على الإنتاج.
5. فحص الفروق بعد replay واختبار جميع الـRPC والسياسات والمحفزات.
6. منع نشر ترحيل إذا فشل replay أو role × operation tests.

لا تنشئ Supabase branch مدفوعًا بالساعة من دون مراجعة السعر؛ الخطة السابقة سجلت تكلفة غير صفرية. يمكن استخدام PostgreSQL 17 في CI إذا كان ذلك متاحًا بلا خدمة مدفوعة.

### 4.2 RLS وعزل الفروع

وجود RLS على جميع الجداول العامة مؤشر جيد، لكن الاختبار الحاسم هو منع:
- قراءة أو تعديل سجلات فرع آخر دون صلاحية صريحة.
- تغيير `branch_id` أو parent FK عبر UPDATE للتحايل على شرط INSERT فقط.
- ربط follow-up أو order أو attachment بمريض من فرع وزيارة من فرع آخر.
- تمرير NULL في علاقة لازمة لتجاوز دالة تحقق.
- استخدام صلاحيات super-admin ضمنيًا من واجهة أو RPC غير مصرح بها.

استمر في الاختبارات الحالية التي تختبر parent/branch integrity، وأضف matrix موحدة للأدوار `anon` و`authenticated` وامتيازات المالك عند الحاجة. يجب ألا يعتمد العزل على إخفاء الأزرار في React.

### 4.3 دوال SECURITY DEFINER

يظهر Advisor 22 تحذيرًا لدوال `SECURITY DEFINER` يمكن استدعاؤها من authenticated. بعضها مقصود لكتابات ذرية مثل إنشاء المريض/الوصفة/الفاتورة/أمر المختبر. المطلوب هو مراجعة كل دالة على حدة:
- تثبيت `search_path` فارغ أو قائمة موثوقة صريحة؛ الحالة المسجلة تقول إن جميع 81 دالة public/private لديها search_path ثابتًا.
- التحقق داخل الدالة من هوية المستخدم والصلاحية والفرع والملكية والروابط بين المريض والزيارة.
- أقل امتيازات ممكنة، وعدم منح `EXECUTE` إلى `anon` بلا سبب موثق.
- تجنب SQL ديناميكي غير محمي، ومعالجة NULL والحدود المالية والتكرار.
- اختبارات نجاح وفشل لكل RPC؛ لا تطبق `REVOKE EXECUTE` بالجملة لأن ذلك قد يعطل العمليات السريرية والمالية.

### 4.4 Storage وRealtime وEdge Functions والإضافات

- لا توجد buckets في Storage في القراءة الحالية. قبل إضافة مرفقات طبية، صمم buckets خاصة، سياسات وصول بالفرع/المريض، روابط موقعة قصيرة العمر، حدود MIME/الحجم، وفحص الملفات؛ لا تجعل ملفات المرضى عامة.
- لا توجد جداول في `supabase_realtime`. ابدأ polling/cache invalidation عند كفايته؛ استخدم Realtime فقط لقائمة الطابور أو حالة المختبر عندما يثبت أن التحديث الفوري يحسن العمل ولا يكشف بيانات لعملاء غير مخولين.
- لا توجد Edge Functions منشورة. لا تنقل منطقًا إلى Edge لمجرد اتباع نمط حديث؛ استخدمها لاحقًا للويبهوكات أو الإشعارات أو التكاملات الخارجية التي تحتاج سرًا خادميًا، مع JWT أو تحقق webhook صريح وحدود معدلات.
- الإضافات المثبتة في القراءة المختصرة: `plpgsql`, `pg_stat_statements`, `uuid-ossp`, `pgcrypto`, `supabase_vault`, `pg_trgm`. لا يظهر أن `pgvector` أو `pgmq` مثبتان، ولا ينبغي تفعيلهما قبل وجود حاجة واضحة. يظهر `pg_cron` في قائمة الإمكانات المتاحة لكن ليس ضمن قائمة الإضافات المثبتة المختصرة؛ تحقّق من الحالة قبل الاعتماد عليه.
- لا توجد ضرورة حالية لـ`pgvector` ما لم يُعتمد بحث دلالي في بروتوكولات سريرية/وثائق داخلية. أي استرجاع سريري يجب أن يعرض المصدر وتاريخه، ويمنع توليد تشخيص/جرعة دون مراجعة بشرية.
- `pgmq`/queue مناسبة مستقبلًا لأعمال خلفية موثوقة (تذكير مواعيد/إعادة محاولة تكامل) عند وجود متطلبات تشغيلية؛ ليست بديلًا عن المعاملة الذرية للفاتورة أو صرف الدواء.

### 4.5 أنماط SQL موصى بها

**أ. RPC ذرية مع مفتاح idempotency** — مثال توضيحي فقط، لا يُنفذ كما هو:
```sql
-- Request key must be unique within the intended business scope.
create unique index if not exists billing_rpc_idempotency_scope_key
  on private.billing_rpc_idempotency (branch_id, request_key);

-- Inside the transaction/function:
-- 1. authenticate and authorize;
-- 2. validate patient/visit/branch relationships;
-- 3. claim request key;
-- 4. write invoice + items + audit event atomically;
-- 5. return the previously stored result on a legitimate retry.
```
لا بد من تصميم conflict behavior بحيث لا تُعاد الفاتورة أو حركة المخزون مرتين، مع عدم السماح بإعادة استخدام المفتاح نفسه لحمولة مختلفة.

**ب. سياسة RLS مرتبطة بالفرع** — نمط مفاهيمي:
```sql
using (
  app_has_perm('visits.read')
  and (select private.app_has_branch_access(visits.branch_id))
)
with check (
  app_has_perm('visits.update')
  and (select private.app_has_branch_access(visits.branch_id))
);
```
ينبغي أن يطابق `WITH CHECK` شروط UPDATE/INSERT، وأن تتحقق الدالة من تغيير parent IDs. يجب استخدام أسماء الصلاحيات الفعلية المعتمدة في المشروع لكل جدول، لا نسخ المثال آليًا.

**ج. فهرس مركب مبني على استعلام حقيقي**
```sql
-- Candidate only; validate with EXPLAIN (ANALYZE, BUFFERS) first.
create index concurrently if not exists visits_branch_created_idx
  on public.visits (branch_id, created_at desc);
```
لا تضف هذا الفهرس قبل مراجعة الفهارس الحالية ونمط الاستعلامات. `CREATE INDEX CONCURRENTLY` لا يُشغّل داخل transaction عادية.

## 5. مقارنة المنافسين والمنصات

الأسعار أدناه أسعار عامة ظهرت في البحث بتاريخ التقرير، ومعظمها بالدولار الأمريكي أو الكندي وموجه لسوق مختلف عن السودان؛ يجب التحقق من الصفحة الرسمية قبل أي قرار تجاري. المقارنة وظيفية وليست ترتيبًا مطلقًا.

### نموذج الإيرادات الممكن لـRoshan
الهدف الأول هو نجاح المركز الفعلي وتخفيض تكلفة التشغيل، لا فرض اشتراك قبل إثبات القيمة. إذا تقرر لاحقًا إتاحة النظام لعيادات أخرى:
1. **Community/self-hosted**: إصدار أساسي مجاني مع وثائق واضحة، مع تحديد مسؤولية التحديث والنسخ الاحتياطي.
2. **Hosted clinic tier**: رسوم ثابتة صغيرة بحسب حجم المنشأة/الفروع بدل تسعير كل موظف، لأن القدرة الشرائية والاتصال قد يختلفان محليًا.
3. **Support & onboarding**: إعداد البيانات، تدريب الموظفين، الاستيراد، والتحديثات كخدمة اختيارية.
4. **Optional integrations**: رسائل تذكير، تكامل مختبرات/دفع، أو تقارير مخصصة، مع توضيح تكلفة الطرف الثالث.
5. **لا تبع بيانات المرضى ولا تستخدمها للإعلانات أو التدريب.** يجب أن يكون التصدير والنسخ الاحتياطي والانتقال بين المزودين متاحًا بصورة آمنة.

لا تُعتمد أي أسعار مقترحة قبل دراسة محلية مع أطباء ومراكز صغيرة، وتكاليف الاتصال والاستضافة والدعم، ومتطلبات الخصوصية والقوانين ذات الصلة.

## 7. توصيات Supabase قابلة للتطبيق

### نمط RPC للكتابات الحساسة
الكتابات التي تجمع أكثر من جدول (تسجيل مريض، إنشاء فاتورة وعناصرها، صرف وصفة وتحديث المخزون، استلام دفعة مخزون، إكمال طلب مختبر) يجب أن تتم داخل معاملة واحدة على مستوى Postgres، مع تحقق صلاحية وفرع وربط الكيانات، ومع مفتاح idempotency حيث يمكن تكرار الطلب بسبب الشبكة أو الضغط المتكرر.

### اختبارات التكامل المطلوبة لكل RPC
- المستخدم غير المسجل/دور `anon`: رفض.
- مستخدم مسجل بلا permission: رفض.
- مستخدم مخول بفرع آخر: رفض.
- Parent ID من فرع مختلف أو علاقة غير متسقة: رفض.
- قيم NULL، كميات سالبة، مبالغ غير finite، كسور غير مسموحة: رفض.
- تكرار الطلب بنفس المفتاح: نتيجة واحدة مستقرة دون تكرار الآثار المالية/المخزنية.
- استدعاء متزامن من جلستين: لا ازدواجية ولا فقد تحديث.
- تحقق أن `anon` لا يملك EXECUTE على RPC الحساسة.

### فهرسة وأداء
1. اجمع الاستعلامات الأكثر تكرارًا/زمنًا من `pg_stat_statements` وقياسات الواجهة.
2. شغّل `EXPLAIN (ANALYZE, BUFFERS)` على بيانات اصطناعية تمثل حجمًا متوقعًا، مع عدم تعريض بيانات المرضى.
3. افحص التداخل بين الفهارس قبل إنشاء جديد.
4. لا تحذف 89 مؤشرًا بناء على Advisor وحده؛ قد تكون الإحصاءات من فترة استخدام قصيرة.
5. راجع pagination وselect columns، خصوصًا patient search وvisits وlab queues وinvoice history.
6. ضع budget لأحجام الاستجابات ومدة الاستعلام، وتجنب تنزيل كامل الجداول للمتصفح.

### سجل التدقيق والخصوصية
- سجل هوية المنفذ، الفعل، الكيان، الفرع، الوقت، وcorrelation/request ID؛ لا تسجل نصوصًا سريرية أو أسرارًا أو token.
- امنع تغيير سجل مالي/سريري بعد التثبيت دون مسار تعديل/إلغاء واضح وسجل تدقيق.
- افصل سجلات التشخيص التقنية عن محتوى المرضى.
- عند استخدام PostHog أو أدوات تحليل، امنع تسجيل أسماء المرضى والمعرفات والنصوص السريرية والـURLs الحساسة والـrequest bodies، ولا تفعل session replay على الشاشات السريرية دون مراجعة صارمة.

## 8. خارطة طريق مرتبة

### P0 — بوابات ما قبل الاستخدام السريري الحقيقي
1. **Replay نظيف للقاعدة:** baseline + migrations مرتبة + استثناء الهوية المنقح + PostgreSQL 17 CI.
2. **تأكيد النشر:** التحقق من SHA المنشور على النطاق القانوني، وعدم تجاوز قيود Vercel المجانية.
3. **بوابة Phase 30:** بعد وصول الكود الصحيح إلى الإنتاج، اختبار إكمال نتيجة مختبر وإنشاء شهادة عبر RPC، ثم فقط تقرير إلغاء الكتابة المباشرة على `lab_order_items` و`medical_certificates`.
4. **RPC audit:** تصنيف الـ22 تحذيرًا حسب المخاطر، اختبار صلاحيات/فرع/روابط لكل دالة، معالجة الحالات عالية المخاطر بأقل تغيير ممكن.
5. **نسخ احتياطي واستعادة:** توثيق ما يمكن نسخه ضمن الخطة الحالية، اختبار restore على بيئة غير إنتاجية، وكتابة runbook للحوادث.
6. **Auth configuration review:** redirect URLs، حماية كلمات المرور المسربة حسب الخطة، rate limits، إعداد البريد، واسترداد الحساب. لا يمكن حسمها من SQL فقط.
7. **اختبار تدفقات E2E اصطناعية:** تسجيل المريض → زيارة → تشخيص/علامات حيوية → وصفة/مختبر → نتيجة → فاتورة/دفع → تدقيق.

### P1 — مكاسب سريعة خلال 1–2 أسبوع عمل
1. توحيد صفحات القوائم في pagination/filter/sort/loading/empty/error states.
2. قياس عدد النقرات والزمن في تسجيل مريض، بدء زيارة، صرف وصفة، استلام مختبر، وتحصيل دفعة.
3. بحث موحد لا يكشف إلا النتائج التي يحق للدور/الفرع رؤيتها، مع اختصارات لوحة مفاتيح متوافقة مع الهاتف.
4. قوالب وصفات منظمة: الشكل الصيدلاني، التركيز، الجرعة، الطريق، التكرار، المدة، الكمية، التعليمات، والتنبيهات. أي جرعات مرتبطة بالوزن/العمر يجب أن تكون مرجعًا مساعدًا معتمدًا يراجعه الطبيب، لا وصفة آلية غير مراقبة.
5. تنبيه واضح عند انتهاء المخزون/قرب الانتهاء، مع فصل المخزون المتاح عن المحجوز/المنصرف.
6. تقارير مالية يومية قابلة للمطابقة بين الفواتير والمدفوعات والصندوق، مع معالجة الإلغاء/الاسترداد.
7. حالات تحميل/خطأ/نجاح موحدة، وتجنب النقر المكرر في عمليات المال والوصفة.
8. مراجعة عربية RTL وإنجليزية LTR على الهاتف، بما في ذلك dialogs والجداول والنماذج الطويلة.

### P2 — تحسينات متوسطة المدى
1. اختبار Playwright/Cypress أو E2E مناسب على أهم 5 رحلات عمل مع بيانات اصطناعية، وتثبيت smoke test بعد كل نشر.
2. توليد أنواع TypeScript من schema الفعلي في CI والتحقق من الانجراف.
3. مراقبة أخطاء التطبيق وCore Web Vitals مع redaction؛ قياس p95 للبحث والزيارات والفواتير.
4. إضافة Storage خاص للمرفقات الطبية فقط بعد تحديد سياسات الوصول والاحتفاظ والنسخ الاحتياطي.
5. إضافة Realtime لطابور الانتظار/حالة المختبر عند إثبات الحاجة؛ وإلا حافظ على الحل الأبسط.
6. توثيق قاموس البيانات ومصدر الحقيقة لكل كيان، خصوصًا الشهادات والأدوية والمخزون.
7. تشغيل فحص اعتماديات دوري وCodeQL، وتحديثات مُختبرة بدل ترقيات شاملة غير مقيدة.

### P3 — تميّز استراتيجي طويل المدى
1. **FHIR تدريجي:** ابدأ بتصدير Patient/Encounter/Observation/MedicationRequest/DiagnosticReport على هيئة FHIR عند الحاجة للتكامل، دون استبدال schema الحالي مباشرة.
2. **Offline resilience محدود:** PWA مع حفظ مسودات غير حساسة محليًا عند الضرورة، ومزامنة محسوبة؛ لا تخزن سجلًا طبيًا كاملًا على جهاز مشترك.
3. **Clinical decision support:** بروتوكولات قابلة للتوثيق والإصدار مع المصدر وتاريخ المراجعة، وحقول تحذير الحساسية/التداخل/الجرعات تحت سيطرة الطبيب.
4. **لوحة جودة تشغيلية:** زمن الانتظار، زمن دورة المختبر، اكتمال الملف، أخطاء المخزون والفوترة، دون استخدام أسماء المرضى في التحليلات.
5. **Multi-clinic offering** فقط بعد ثبات المركز الأول: إعداد tenant/branch واضح، ترحيل وتصدير، onboarding، support model وتسعير محلي.
6. **بحث دلالي/AI** بعد تأسيس حوكمة بيانات قوية: pgvector اختياري للوثائق والبروتوكولات غير المعرفّة، citations إلزامية، وعدم كتابة نتائج سريرية تلقائيًا.

## 9. مبادئ تصميم UX خاصة بروشان

- صمّم بحسب المهمة اليومية والدور، لا بحسب أسماء الجداول.
- شاشة الطبيب: قائمة انتظار → ملخص مريض مختصر → الزيارة الحالية → علامات حيوية/تاريخ/حساسية → تشخيص وخطة → وصفة/تحاليل → حفظ/إنهاء، مع أقل انتقال بين الصفحات.
- الاستقبال: تسجيل/بحث مريض، فتح زيارة، رقم طابور واضح، توجيه إلى الخدمة، حالة الفاتورة؛ لا تعرض تفاصيل سريرية غير لازمة.
- المختبر: قائمة طلبات بحسب الأولوية والحالة، إدخال نتائج مهيكل، وحدود مرجعية حسب العمر/الجنس حيث تنطبق، تحقق قبل الإكمال، ومنع الإكمال المكرر.
- الصيدلية: صرف مرتبط بوصفة مؤكدة، تحقق مخزون الدفعة وتاريخ الانتهاء، تحديث stock movement والفاتورة ذريًا.
- الحسابات: فصل الاستحقاق عن التحصيل وعن حركة الصندوق؛ لا تجعل تعديل فاتورة يغير دفتر النقد تلقائيًا دون سجل صريح.
- اجعل الحالات الخطرة (فرع غير صحيح، مريض مختلف، نقص مخزون، تعارض دفعة) ظاهرة قبل تأكيد العملية.
- حافظ على واجهة RTL متماسكة، تباين جيد، أهداف لمس كبيرة، أداء مقبول على هاتف منخفض الموارد، وعدم الاعتماد على hover وحده.

## 10. قرارات لا ينبغي اتخاذها الآن

- لا تستبدل Supabase أو React أو TanStack دون قياس مشكلة فعلية.
- لا تنقل النظام كاملًا إلى Medplum/OpenEMR/ERPNext لمجرد أنها مشاريع ناضجة.
- لا تثبت `pgvector` أو `pgmq` أو توسع Realtime دون حالة استخدام واضحة.
- لا ترفع الخطة إلى خدمة مدفوعة ولا تنشئ مشروع/branch يستهلك المال من دون معرفة السعر.
- لا تطبق migrations المرشحة غير المثبتة على الإنتاج لمجرد أنها مدمجة في Git.
- لا تحذف مؤشرات أو دوال أو جداول بصورة جماعية استنادًا إلى تحذير آلي.
- لا تدّعِ أن اجتياز CI أو كون التطبيق يعمل في جلسة واحدة يثبت الجاهزية السريرية.
