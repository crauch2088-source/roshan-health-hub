# Roshan Health Hub — GitHub Spec Kit Integration

**Pinned release:** GitHub Spec Kit CLI 1.2.6  
**Integration:** none (official agent-neutral/shared-scaffolding mode)  
**Scope:** repository engineering workflow only; not an application/runtime dependency.

## What is installed

The .specify/ directory was generated by running the official CLI against the Roshan repository clone with:

    specify init --here --force --non-interactive --integration none --ignore-agent-tools

The committed baseline includes official shared Bash scripts, feature/plan/task/checklist/constitution templates, the bundled speckit workflow, integration metadata, managed-file manifests, and the project Constitution. The managed files are tracked by the official Spec Kit manifest; do not hand-edit managed templates/scripts without updating them through the CLI.

The CLI was then run against the project clone:

    specify integration status

Observed result: Integration status: OK; default integration none; installed integrations none; zero modified managed files; zero missing managed files; zero invalid manifest paths; zero unchecked manifests. The CLI reported version 1.2.6.

## Why none is intentional

The official none integration installs shared scaffolding without agent-specific commands, hooks, IDE configuration, or a coding-agent runtime. The owner does not need to create a Codespace, sign into a model provider, configure a local agent, or run terminal commands.

ChatGPT operates the specification lifecycle directly against the connected GitHub repository:
1. Inspect current source, tests, migrations, permission definitions, and the relevant Master Plan phase.
2. Draft spec.md from the approved requirement, keeping unknowns explicitly marked.
3. Resolve ambiguities with the owner before technical design.
4. Write plan.md, research/data-model/contracts/quickstart artifacts only when justified by the existing system.
5. Derive tasks.md with exact file paths and verification evidence.
6. Implement on a separate branch with regression coverage and one atomic commit per logical task.
7. Review the exact PR head and CI results; use analysis/convergence concepts as a requirements-to-implementation review, not as a claim that none dispatches an agent.

The bundled workflow is present, but none does not install interactive /speckit.* commands. No such commands are expected or required for this operating model.

## Source-of-truth boundaries

- docs/MASTER_PLAN.md: project roadmap, sequencing, and execution status.
- AGENTS.md: repository operating instructions.
- .specify/memory/constitution.md: durable engineering principles.
- specs/NNN-feature/: requirements and feature-specific design artifacts.
- docs/: durable audit, reconciliation, and execution records.

A feature spec links to its Master Plan phase rather than copying the roadmap. The initial pilot is specs/001-clinical-document-printing/spec.md, based on Phase 53. It remains Draft; no plan/task list is authorized until the listed clarifications and current-source contract review are complete.

## CLI installation for reproducible validation

The CLI is a developer/CI tool, not an app dependency:

    uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@v1.2.6
    specify version
    specify integration status

The dedicated workflow .github/workflows/spec-kit-validation.yml repeats the pinned install, validates committed integration state and managed files, runs the repository contract test, and smoke-initializes a disposable agent-neutral project. It does not connect to Supabase or Vercel and does not trigger an application deployment.

## Safety constraints

- Never put real patient, clinical, financial, staff identity, credential, private-key, or production-export data into specs, fixtures, prompts, logs, or QR payloads.
- Use synthetic fixtures only. The Spec Kit workflow must never access production credentials or execute Supabase SQL.
- A specification, plan, or checked task is not authorization to deploy, migrate, change grants/RLS, mutate Auth/Storage, or write production business data.
- Preserve existing backup, migration-provenance, authenticated clinical E2E, and staff-UAT release gates.
- Keep Spec Kit out of package.json dependencies and production bundles.
